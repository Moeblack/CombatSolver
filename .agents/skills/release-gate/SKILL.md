# CombatSolver 发布与打包

## 适用边界

用户明确要求版本、ZIP、创意工坊上传、发布候选或完整发布门禁时使用。项目 `AGENTS.md` 规定的“实现/修复后默认最小发包”视为用户明确授权；用户明确说不发包时不触发。

先确认用户要求的是哪一级：

- **构建/打包**：版本同步、Release 构建、最小 ZIP 和内容检查。
- **创意工坊上传**：使用当前已定版的最新版更新创意工坊内容，并提交面向玩家的更新说明；不自动增加完整门禁或发布后复测。
- **完整发布门禁**：在构建/打包基础上增加覆盖、回归、可见 Steam、干净安装。

用户指定较窄范围时不要擅自扩成完整发布。

## 1. 版本与来源

- 构建前同步 `CombatSolver.csproj`、`CombatSolver.json` 和开发说明中的目标版本。
- 提交源码、fixture 和文档后，从该提交构建；构建后又改源码则重新构建。
- “当前最新版”指仓库中版本已同步、已经提交并完成最小发包的最高版本，不是创意工坊暂存目录里上次留下的内容。当前存在应随本次发布进入的未定版改动时，先按项目规则完成补丁版本和最小发包，再上传；只有重新上传同一版页面资料时才沿用现有版本。
- Release 编译成功不能替代目标修复的语义或行为证据。
- 普通发布记录使用版本、source commit、构建时间和预定 ZIP 文件清单即可。只有发布渠道、来源争议或用户明确要求时才增加 SHA-256。

## 2. Release 构建

```powershell
dotnet clean -c Release
pwsh -NoProfile -File tools\build-local-stack.ps1 -Configuration Release
```

不要从游戏 Mods 目录反向复制 DLL，不复用未知来源旧构建。版本一致性在构建前由源码中的项目版本、manifest 和当前提交确定；构建成功后不再反射或读取 DLL 版本重复确认。

## 3. 最小 ZIP

当前 `has_pck=false`。ZIP 默认只包含：

- `CombatSolver.json`；
- 当前 Release `CombatSolver.dll`；
- 根目录 `THIRD_PARTY_NOTICES.md`；
- manifest 明确要求的其他资产（若将来新增）。

`THIRD_PARTY_NOTICES.md` 是 Random Foreseer 书面许可要求的二进制分发文件，不得从任何 ZIP、独立下载包或创意工坊内容中省略。不得包含其他源码、日志、问题包、存档、coverage fixture、游戏依赖 DLL、`bin/obj/.godot/.local` 或旧版本 DLL。打包命令必须显式只写入上述预定文件；命令成功就是打包完成证据，不重新打开、解压或检查 ZIP 条目与 DLL 版本。

目标行为已经在当前行为源码上通过后，若提交前后只改版本号、文档或发布元数据，Release 构建和 ZIP 创建不触发同一场景复测。行为源码、编译配置、依赖或测试输入变化时才重新运行对应测试。

## 4. 创意工坊上传

用户说“上传创意工坊”或“更新创意工坊”时，视为已授权这一次外部上传，直接执行，不再询问是否确认。默认工具与暂存目录为：

- `D:\Desktop\sts2mod\ModUploader-win-x64\ModUploader.exe`；
- `D:\Desktop\sts2mod\ModUploader-win-x64\CombatSolverWorkshop`。

上传前只做一次本地暂存：

1. 将当前最新版的 `CombatSolver.json`、刚完成的 Release `CombatSolver.dll` 和根目录 `THIRD_PARTY_NOTICES.md` 写入 `CombatSolverWorkshop/content/`，不得沿用该目录中的旧二进制判断版本；
2. 保留现有标题、长描述、作者、封面、效果图、标签、依赖和可见性，除非当前请求或确切兼容性变化要求修改；
3. 把本次更新说明写入 `workshop.json` 的 `changeNote`，然后执行一次 `ModUploader.exe upload -w .\CombatSolverWorkshop`。

上传命令报告成功就是完成证据。不要重新打开创意工坊页面、重新下载订阅内容、检查远端条目、再次读取版本或重复上传；命令失败时报告真实错误，修正明确原因后才重试。

### 更新说明口径

更新范围是创意工坊上次已发布版本之后到当前最新版。`docs/DEVELOPMENT_NOTES.md`、相关提交和实际功能改动是事实来源，但创意工坊更新说明必须重新提炼，不能把开发记录原样复制过去。

只写玩家在游戏中能理解和感知的内容：

- 新功能、新支持内容与路线质量改进；
- 会改变实战结果的错误修复；
- UI、操作、动画、提示和性能体验变化；
- 游戏版本、前置依赖或已知限制中确实影响使用的变化。

不要写类名、方法名、职责拆分、状态所有权、Beam/镜像内部实现、内存或 GC 机制、runId、提交号、测试矩阵、构建和打包过程。性能变化只描述玩家体验，例如“降低长时间计算后的卡顿”，不写内部回收方案或基准流水账。跨多个版本时按“新增 / 优化 / 修复 / 兼容性”合并同类内容，不逐版罗列开发过程。不确定是否已经进入当前发布版的内容不写；确实没有玩家可见变化时明确写“本次更新没有游戏内功能变化”，不编造更新。

## 5. 完整发布门禁

只有用户要求完整验收或正式发布时执行：

1. 运行 `tools/verify-refactor-boundaries.ps1`；
2. 对当前 DLL 运行 CoverageCatalog 全 verify；
3. 运行目标严格差分、相关类型族、增量等价和至少一场完整自动部署；
4. 跑一场稳定长线质量基准，断言跨回合复用与零非预期重算；
5. 使用正常可见 Steam 会话验证 UI、输入、动画、部署、GC、帧和路线质量；性能样本关闭 `VerifyIncrementalSearch` 与详细诊断；
6. 从 ZIP 干净安装到已确认的精确 Mod 目录并做最终冒烟。

CoverageCatalog 生成受控文件变化时，审查并提交，再从最终提交重新构建。不要用旧 DLL 配新源码。

## 6. 安装安全

- 解析并确认精确 Mod 目标目录，只处理该目录内已知 manifest/DLL。
- 目录含未知文件时停止，不递归清空。
- 从刚生成的 ZIP 安装，确认加载日志中的版本和程序集路径。
- 冒烟后如再改源码或 manifest，当前候选失效。

## 7. 发布结论

完整发布结论至少报告：版本/source commit、ZIP 路径与文件清单、构建结果、实际执行的覆盖/fixture/完整战斗/可见 Steam/干净安装，以及未执行项。创意工坊上传另报告版本、更新说明摘要和上传命令结果；不把本地暂存写成远端成功。

以下情况不能写“完整门禁通过”：版本不一致、目标修复只有编译证据、增量与完整回放不一致、完整部署出现未解释重算、ZIP 混入非发布文件，或性能/UI 改动没有可见验收。
